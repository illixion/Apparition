# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A personal, LAN-only "app store": a single-file Node.js HTTP server that builds dev iOS / visionOS / tvOS / iPad apps from local git checkouts, signs and installs them onto physical Apple devices, and tracks what each device is running. The web UI at `127.0.0.1:<port>` shows every configured repo, its current git HEAD, and each target device's install status, with one-click "Build + Install".

It orchestrates two external tools: `bin/build-and-sign` (xcodebuild + codesign + deploy) and `xcrun devicectl` (device inventory + install). It is not itself an Xcode project.

## Running & deploying changes

- **No package.json, no dependencies, no build step, no linter.** Tests: `node --test 'test/*.test.js'` (quote the glob; `node --test test/` does not work, and a bare `node --test` also walks `data/build-clones`). `server.js` only listens when run directly; tests `require` it, with `APPSTORE_CONFIG`/`APPSTORE_DATA`/`DEBUGTRACE_KEY_DIR` pointed at a temp dir (see `test/helpers.js`). The freshness logic lives in `public/freshness.js` so tests can load it. Pure Node stdlib (`node:http`, `node:fs`, `node:child_process`). `data/` (runtime state, logs, per-branch build clones) is gitignored — it's machine-local and regenerated at runtime.
- Runs as a launchd LaunchAgent you install yourself (see the README) with `KeepAlive` — so it auto-restarts on crash or when you kill it. Point the agent's stdout/stderr at a log file.
- **After editing `server.js`:** restart the agent — `launchctl kickstart -k gui/$(id -u)/<agent label>` (or just `kill <pid>` and KeepAlive respawns it with the new code). Do **not** launch `node server.js` manually to test — the agent already holds the port and your process will die with `EADDRINUSE`.
- **After editing anything in `public/`:** no restart needed — static files are read from disk on every request. Just reload the page.
- Listens on `127.0.0.1` only, on `config.json`'s `port` (currently 8484). **`config.json` changes require a restart.**
- Before restarting, check `GET /api/state` for `activeBuild`/`queued` — a restart marks any in-flight build as failed.

## Configuration (`config.json`)

- `deployDefaults` (top level, and per repo; a repo's keys override the top level): which deploy-menu checkboxes start ticked. Keys are `mcp` (default `true`: `--mcp`, debug server attached, implies launch), `launch` (`--run`), `buildDebug` (`--debug`, Debug configuration) and `inject` (`--inject`). Built-in defaults are MCP on, the rest off. Non-boolean values are ignored. The store always passes `--mcp` or `--no-mcp` to build-and-sign, so its own `MCP_DEFAULT` never turns an install-only deploy into an MCP session.

Defines everything the server operates on. Per repo: `name`, `path` (git checkout on disk), `branches` (offered in UI), and `platforms[]` — each `{ platform, bundleId, device }` where `device` is a `devicectl` device name. Only apps whose bundle id starts with one of `bundlePrefix` (a string, or an array for repos outside the main namespace — e.g. `org.example.*` alongside `com.example.*`) are tracked from device inventory.

`platform` is passed through as the `PLATFORM` environment variable and reaches xcodebuild as `-destination generic/platform=$PLATFORM` — *unless* the repo's `build-signing.conf` intercepts it first. A repo conf may therefore define **aliases that are not real Xcode platforms**, which is how one build reaches several destinations: a conf can map `iPad` and `visionOS` back to `PLATFORM=iOS` with a different `DEVICE_NAME` (visionOS runs the iPadOS binary under "Designed for iPad", so there is no separate platform to build for). When a platform name here is not one `xcodebuild` recognises, look for it in that repo's conf.

`cloneExclude` (optional, per repo) lists paths, relative to the repo root, that a build clone leaves out (`["build", "target", "clients/android"]`). `cp -c` shares data blocks but still makes an inode per file, so cloning a repo with hundreds of thousands of files took over a minute (RegentChat: 357k files, 78 s). List only what the build regenerates or never reads, and keep the caches a `PRE_BUILD_HOOK` reuses; tracked files under an excluded path come back from the checkout, so exclude directories, not tracked sources you need. Only builds of a non-checked-out branch clone, so this does nothing for the current branch.

`buildSettings` (optional, per repo) becomes repeatable `--set KEY=VALUE` args to `build-and-sign`. It's either an array (applied to every branch) or an object `{ "<branch>": [...], "*": [...] }` for per-branch settings — needed when a flag only compiles on some branches (a feature flag that only exists on a feature branch, say).

Either form's value may itself be an object `{ "<platform>": [...], "*": [...] }` to scope settings per platform within a branch. That's for a repo whose platforms are **separate targets linking different dependencies**: an iOS client that is its own target without a dependency the visionOS target links will fail on a flag for that dependency instead of ignoring it. This scoping has to live here rather than in the repo conf, because these `--set` args land *after* the conf on the xcodebuild line and therefore win — a platform-blind setting here cannot be undone downstream.

## Architecture (`server.js`, single file)

- **Persistent state** → `data/state.json`, written atomically (tmp + rename) and debounced 250ms via `saveState()`. Shape: `installs[device][bundleId]` (the store's own ledger of what it built — `repo/branch/commit/version/buildNo`), `deviceApps[device]` (last `devicectl` inventory), `devices`, `builds[]` (capped at 200), `nextBuildId`. On startup, any build left `running`/`queued` from a previous process is marked `failed`.
- **Build queue is serialized per repo, not globally** — `repoQueues: Map<repo, {queue[], activeId}>`, drained by `pump(repo)`. Same-repo builds must run one at a time because `build-and-sign` writes into the repo's shared `$PROJECT_ROOT/build`; different repos build concurrently on purpose, so deploying several apps to their own devices at once is a real parallel build, not just parallel UI. `build-and-sign` also mutates the login keychain search list, a global (non-per-repo) resource — that race is closed on the `build-and-sign` side, not here: it takes a cross-process directory-based mutex (`bin/build-and-sign`, `SIGNING_LOCK_DIR`) around the setup-keychain..cleanup window, so two repos' builds can run `xcodebuild` concurrently and still queue safely through the short signing tail. Do not go back to one global queue in server.js — that was tried and undoes the intended cross-repo parallelism; the keychain race is handled elsewhere.
- **`executeBuild()`** never checks out a different branch in the repo's main working tree. If `job.branch` differs from the branch currently checked out there, it builds from a dedicated clone instead (`ensureBuildClone()`, parked under `data/build-clones/<repo>/<branch>`). The clone is disposable and rebuilt fresh on *every* build — wiped (`rm -rf`) and reseeded via `cp -cR`, an APFS copy-on-write clonefile, so it's instant and free of extra disk until the copies diverge — then fetches the branch from the main repo (a local-path git remote), checks it out, and `reset --hard`s to it. It's rebuilt every time rather than kept around and incrementally resynced because git refuses to `fetch` into a ref that's already checked out in a non-bare repo: a clone left checked out on `branch` from its previous build would fail to fetch that same branch's updates on the next one. Unlike `git worktree add` (tracked files only), `cp -cR` brings over *everything*, including gitignored `build-signing.conf` (local cert/profile paths, needed or `build-and-sign` fails with `PROJECT_PATH is not set`) and any already-fetched deps under a repo's `repos/` — so a repo's `PRE_BUILD_HOOK` dependency-setup script sees them present and skips re-cloning instead of colliding with a half-populated fresh checkout. This lets the main checkout stay dirty (e.g. mid-edit by an LLM) while an unrelated branch builds untouched. Building `job.branch === 'current'` or the branch the main tree already has checked out still builds directly from the repo path — its dirty state is intentional there. It then spawns `/bin/bash ~/bin/build-and-sign [--set ...]` with `cwd` = the resolved build directory (repo path or clone) and `env.PLATFORM`. Output is streamed both to `data/logs/build-<id>.log` and an in-memory `liveLogs` map (last ~5 builds). The installed version/build number is read back from the **signed IPA's Info.plist** (the staging copy predates the version stamp).
- **Live `ChildProcess` handles live in the `procs` map keyed by build id — never on the job object**, because jobs are JSON-serialized into state. Cancellation looks them up there.
- **Device I/O** (`devicectlJson`): runs `xcrun devicectl ... --json-output <tmpfile>`, reads and parses the temp file (devicectl writes JSON to a file, not stdout). `gitInfo()` is cached 10s per repo path.
- **HTTP API:** `GET /api/state`, `POST /api/build` `{repo, targets:[{device,branch}], run, deploy}` (also accepts singular `device`/`branch` as an alias for a one-target batch) → `{jobs:[...]}`, `GET /api/builds/:id/log?offset=N` (incremental tail), `POST /api/builds/:id/cancel`, `POST /api/refresh-devices`, plus static serving from `public/`. A `targets` array of more than one device fans out into a batch (`state.builds[].batchId` shared across the group) that queues together but still runs one job at a time — see the build-queue note above. Branch is per-target, not per-batch, so a repo's `deviceBranches` mapping (e.g. building the headset from a feature branch while the phone stays on `main`) can be deployed in one batch.

## The version-freshness model (important, non-obvious)

Dev builds keep a **static** `CFBundleShortVersionString` (`"1.0"`), so the version string can never reveal whether a device is stale. Instead, `build-and-sign` stamps the **git short SHA into `CFBundleVersion`**, which `devicectl` reports back as `buildNo` (e.g. `"304c1c9"`, or `"24ca4f4-dirty"`). The freshness check compares that on-device SHA against the repo's HEAD commit (`git.commit`), falling back to the store ledger's recorded `commit` when `devicectl` gives a non-git buildNo. The frontend (`public/index.html`, `render()`) uses this to show up-to-date / out-of-date / dirty / other-branch state per platform. When touching version/staleness logic, reason about the SHA, not the version string.

## Auth (`lib/auth.js`) and live debugging (`lib/debug.js`)

- **Password.** `passwordHash` (scrypt, from `node server.js set-password`) turns the gate on; with none, everything is open and the page shows a banner. Sessions are a random cookie (`HttpOnly`, `SameSite=Strict`, `Secure` behind HTTPS); only their SHA-256 is stored, in `data/sessions.json` (mode 600), tied to a fingerprint of the current password hash. Five failures lock logins for 60 s globally (behind `tailscale serve` every client is 127.0.0.1). Any non-GET with a foreign `Origin` is refused.
- **What skips the session:** `/login` and the icons; `POST /api/traces` (signature-verified); and `/ota/<slug>/manifest.plist` and `/ota/<slug>.ipa` with a valid `?t=<exp>.<hmac>` (`auth.signPath`, 1 h, secret in `data/secret`). installd can't send cookies, so every OTA link the server hands out (`/ota` page, `GET /api/ota/<slug>/link`, the IPA URL inside a manifest) is signed. Don't build OTA URLs in the browser.
- **Debugging.** `debug.discover()` runs `config.debugtraceTool discover` (DebugTrace's `debugtrace-mcp`), cached 5 s. Apps are addressed by **key id**; the URL comes from discovery and the bearer token from the ledger's `commandToken`, so the browser can't point the proxy at another host. Routes: `GET /api/debug/apps`, `GET /api/debug/<keyId>/help`, `POST /api/debug/<keyId>/call {endpoint, arguments}` (binary replies are passed through with a locked-down CSP), and `GET /api/debug/<keyId>/logs?level=&contains=`, an SSE stream that long-polls the app's `_logs afterSequence= waitSeconds=20` and survives the app going quiet or relaunching. `/api/state` carries the last discovery as `debugApps`; `/api/debug/apps` also returns `clientName`, the name the device's "Allow debug access?" prompt shows for this page.
- **Call timeout (`CALL_TIMEOUT_MS`, 90 s).** The first call from the page waits on that on-device prompt (DebugTrace gives up after 60 s), and `_profile` then samples for up to 10 s, so the proxy waits 90 s. A timeout is a 504 `{code: "timeout"}` whose hint points at the prompt. Don't lower it below 75 s.
- **Testing without a device.** `test/fixtures/fake-debug-app.js` is a DebugTraceServer stand-in (help, `_info`, `_logs`, `_profile`, `_memory` with drifting numbers, an optional approval wait or refusal). `node test/fixtures/debug-sandbox.js --port 8499 [--approval-ms 7000] [--approval timeout]` runs a separate store on temp config/data/ledger pointed at it, so the Debug view can be worked on without touching the live service.

## Frontend (`public/`)

`index.html` is a single self-contained file — vanilla JS, no framework, no build — with four views routed by hash: `#deploy`, `#debug[/<keyId>]`, `#traces`, `#history`. It polls `GET /api/state` every 4s and the open build log every 1.2s; the Debug view polls `/api/debug/apps` every 5s and holds one `EventSource` for the selected app.

The Debug console has five tabs: Log (the SSE tail), **Profile** and **Memory** (first-class views of `_profile` and `_memory`), Endpoints (the generic browser/caller for every endpoint, raw JSON) and Info. Profile and Memory state is kept per app in `D.per[keyId]`, so switching apps keeps a profile and the memory snapshots.
- **Profile:** argument controls, then one card per thread in the order returned, with a busy bar and three views: hot stacks (an icicle merged from the top-N `hotStacks` by common prefix, widths as shares of the stacks shown, plus collapsible call chains with the leaf emphasized), self time and inclusive time. Long Swift/C++ signatures are shortened by `shortName()` (`f(near:radius:)`), with the full text in `title`. "Your code" (violet, `--own`) vs system (slate, `--sys`) comes from `codeOwner()`: the app's name from `_info` matched against row images, plus non-Apple Swift module prefixes (statically linked packages like RAVEInput). "Copy as text" gives the full-name report for pasting to an agent.
- **Memory:** "Take snapshot" appends a `_memory` reading; any snapshot can be shown and compared with another (the first is the baseline by default), and every number then carries a delta. Headroom (`availableBytes`) is the hero, with footprint, peak and the baseline's footprint on one bar.
- **Slow calls:** past the predictable part (the sampling time) plus 2.5 s, the page says the device may be showing "Allow debug access?" for `clientName`. Errors from the app render through `errorHTML()`: a plain title, the message, the app's `hint`, and Try again. `login.html` is the sign-in page. `favicon.svg` / `favicon.ico` / `apple-touch-icon.png` / `mask-icon.svg` are the triangle brand icons referenced from `<head>`.

## Debug traces (`/api/traces`)

Apps built with the DebugTrace package (`illixion/DebugTrace`) upload trace zips from their Debug Trace sheet; the web UI's Debug traces section lists them and also accepts a dropped `.zip` (e.g. one shared by AirDrop). Since build-and-sign gives every dev build a key, Upload works however the app was launched — no `--log`/`--mcp` needed.

- **Keys:** `build-and-sign` (Step 4.7) generates a fresh Ed25519 pair per build of a DebugTrace app, skipping `--distribution`. The private half goes into `DebugTraceCredential.plist` in the `.app` (sealed by codesign) along with `DEBUGTRACE_UPLOAD_URL` from `global.conf`. The public half goes into the **key ledger**: `~/.local/state/debugtrace/keys/<keyId>.json` (`DEBUGTRACE_KEY_DIR` overrides), recording `{publicKey, bundleId, build, platform, configuration, branch, device}`. The ledger is written by build-and-sign itself, so builds run from a terminal verify too, not only store builds.
- **dSYM archive:** after a successful install of a DebugTrace app, `build-and-sign` (`archive_dsyms`) clones the build's `*.dSYM` into `~/.local/state/debugtrace/dsyms/<bundleId>@<device>/` (`DEBUGTRACE_DSYM_DIR` overrides) with a `uuids.json` of binary UUID → DWARF file. One slot per app and device, replaced by the next install to that device, so a device that is not updated can still have its MetricKit crash reports (`crashes/*.json` in a trace) symbolicated with DebugTrace's `Tools/debugtrace-symbolicate <traceId>`. `--no-deploy`, `--sign-only` and `--distribution` keep nothing. The store itself does not symbolicate.
- **Verification (`verifyTrace`):** the zip is parsed in-process (central directory, stored/deflate only, no zip64, every inflate capped at the manifest's declared size), never with `unzip`. A trace is kept only when `manifest.sig` verifies against the ledger key, the manifest's `app.bundleId`/`app.build` equal the ledger's, and the zip holds exactly `manifest.json`, `manifest.sig` and the listed files, each with a matching size and SHA-256. Unsigned traces (Xcode builds) are refused with 403; share those as files.
- **What a signature proves:** the private key ships in the IPA and `/ota` serves IPAs to the tailnet, so "a build this Mac produced, and which one", not "a genuine device".
- **Storage:** `data/traces/<traceId>/` = `trace.zip` (as uploaded), `files/` (extracted, for reading directly — agents can `cat` `files/logs.txt`), `meta.json`. Written as `.incoming-<id>` and renamed. The newest 300 are kept. Re-uploading a trace id returns the existing record with `duplicate: true`.
- **API:** `POST /api/traces` (raw zip body, ≤ 64 MB; `X-DebugTrace-Source: web` marks UI drops) → `201 {ok, trace}` or `{error: "why"}`; `GET /api/traces`; `GET /api/traces/<id>.zip`; `GET /api/traces/<id>/files/<path>` (text served as `text/plain` with `nosniff` + a `default-src 'none'` CSP, never as HTML, since the content came from a device); `POST /api/traces/<id>/delete`. Behind `tailscale serve` the uploader's `Tailscale-User-Login` is recorded.

## Crash logs from devices (`lib/crashlogs.js`, `/api/crashlogs`)

A poller (every `crashLogs.intervalSeconds`, default 300, first look 15 s after start) pulls each configured device's `systemCrashLogs` with `devicectl device info files` + `copy from`, keeps the **app crashes** (the `.ips` header's `bundleID` starts with a tracked prefix) and ignores the rest. `crashLogs` in `config.json`: `enabled` (default true), `intervalSeconds`, `maxAgeDays` (14), `backfillDays` (3: how far back the first look at a device goes).

- **Why besides the traces' MetricKit reports:** the `.ips` is the full crash log with Apple's frames symbolicated, and on tvOS (no MetricKit) it is the only crash report there is. The `.ips` files sit under `Retired/` once Xcode has seen them, so that folder is listed too. A watch's logs appear in its iPhone's list under `ProxiedDevice-…/`.
- **High-water mark per device** (`pull[device].since` + the names already seen at that second), so a poll copies what is new and nothing twice; at most `perPoll` (100) copies a poll, oldest first, so the first poll of a busy device finishes over a few polls. A failed copy does not advance the mark.
- **Failures back off** (2^n minutes, to 30) and show in `pull[device].error` and on the page: an asleep or away device, `The connection to the remote device was interrupted`, or a watch's `has not been unlocked recently`. Measured 2026-10-09: listing and copying worked on a locked, sleeping iPhone; only installing is expected to need an unlock (untested).
- **Symbolicated at pull time** by DebugTrace's `Tools/debugtrace-symbolicate` (next to `debugtraceTool`, or `symbolicateTool`) against the dSYM archive, so the text exists before an update replaces the device's build. Stored as `data/crashlogs/<device>/<name>-<id>.ips` and `.txt`; `index.json` holds the entries (newest 300 kept).
- **Linked to the MetricKit trace** of the same crash by bundle id, `pid` and (27+: within 10 min; older reports have only a local time, so within 48 h). Re-run after every pull and every trace upload, since either can arrive first.
- **API:** `GET /api/crashlogs` → `{crashLogs, pull}`; `POST /api/crashlogs/refresh`; `GET /api/crashlogs/<id>/ips` and `/symbolicated` (served as `text/plain`, never HTML). Behind the password like the rest, except that nothing here skips the session. `test/crashlogs.test.js` drives it with a fake device.

## External dependencies (must exist on the host)

- **`bin/build-and-sign`** — (lives in this repo; a local `~/bin/build-and-sign` should be a symlink to it so the terminal and the store run the same code) bash script that builds, signs, and deploys. Reads signing material from `~/.config/build-signing/global.conf` plus each repo's `scripts/build-signing.conf` (or `build-signing.conf`). Repo-specific behavior belongs in that conf (`PRE_BUILD_HOOK`, `EXTRA_BUILD_SETTINGS`), never in `server.js`.
- **Build output is per checkout, locked, and reaped** (2026-10-08). `build-and-sign` puts DerivedData in `<checkout>/build/DerivedData` (and `DerivedData-inject` for `--inject`), never under the git common dir: it used to, which made every worktree of a repo build into the main checkout's cache, with different sources and package clones at other paths, so they rebuilt each other's products and corrupted them when concurrent. It also takes a per-checkout lock (`build/.build-and-sign.lock`, pid-verified, a dead holder's is stolen) so two runs in one checkout queue instead of colliding; `--sign-dylib` skips it. This covers builds the store's per-repo queue never sees (an agent running the script in a worktree). Storage: `apple-worktree remove` deletes a worktree's build with it and `apple-worktree gc` (also run by `new`) drops idle worktrees' build output; the store deletes a build clone's DerivedData after the build (an `--inject` build keeps `DerivedData-inject`, which patches compile against) and deletes clones untouched for `cloneMaxAgeDays` (config, default 7), never one in use. Don't point an agent's own `xcodebuild -derivedDataPath` at `build/DerivedData` while a deploy may run there; use `build-and-sign --no-deploy`, which takes the lock.
- **`xcrun devicectl`** (Xcode) — device inventory and install; target devices must be paired and reachable.
- Every repo in `config.json` must be a real git checkout on disk with a valid `build-signing.conf`.
